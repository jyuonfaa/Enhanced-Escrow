Enhanced Escrow — Chapter 1: Architecture

1. Project Vision & Core Logic

The Enhanced Escrow System is a decentralized trust platform built to solve the "Stalemate Problem" in localized peer-to-peer commerce. It operates as a Digital Intermediary that manages capital flow through physical real-world events.

1.1 The Failsafe Logic

In traditional trade, either the Buyer trusts the Seller by paying first, or the Seller trusts the Buyer by shipping first. Our software removes this requirement. Funds are captured by the system and only released when Multi-Factor Verification (Photo + OTP) is satisfied.

🧠 THE STATE TRANSITION MODEL

Every transaction in the system is a State Machine. A transaction cannot "jump" from Pending to Completed. It must satisfy each intermediate state, ensuring that logistics and payment are always in sync.

1.2 The Database Schema (Prisma)

The software uses a strictly typed PostgreSQL schema. Observe how the Transaction table acts as the nexus connecting User (Buyer/Seller/Agent) and Product.

model Transaction { id Int @id @default(autoincrement()) status String // PENDING, ESCROW_HELD, AWAITING_OTP, DELIVERED, COMPLETED amount Float escrowCode String? // The OTP (Encrypted in transit) deliveryPhotoUrl String? // The visual proof deliveredAt DateTime? // The 24h timer trigger }

Enhanced Escrow — Chapter 5: Engine

5. The Escrow Transaction Engine

This chapter explores the heart of the system—the sequential logic that moves money safely across the network.

5.1 State 1: PENDING & Initialization

When the Buyer clicks "Buy", the system generates a unique Transaction ID and maps the current Product price to the amount field. This prevents "Price Baiting" where a seller changes the price after the purchase.

5.2 State 2: ESCROW_HELD (Capital Locking)

The system "Captures" the funds. In our prototype, this is simulated as a direct state change. In production, this happens only after a Success webhook from the Payment Gateway (Paystack/Stripe).

⚠️ SECURITY GUARDRAIL

Once a transaction is in ESCROW_HELD, the Buyer cannot cancel it manually. This protects the Seller and Agent who may have already spent resources on logistics. Any reversal must now go through a Dispute.

5.3 State 3: AWAITING_OTP (The Proxy Arrival)

The Agent triggers this by uploading photo proof. This is a Physical Oracle Event—the system now "knows" the courier is at the doorstep.

Enhanced Escrow — Chapter 6: Verification

6. Verification: The Cryptographic Handover

This chapter focuses on the **Agent Verification Logic**, which is the system's primary defense against "Fake Delivery" claims.

6.1 The OTP Lifecycle

The OTP (One Time Password) is a 6-digit random string generated only when the Agent uploads the photo. It is never stored in plaintext in the frontend state for the Agent or Seller.

Test: Verification Integrity

  1. 1 Agent: Enter an incorrect OTP. Expect a 400 Bad Request.
  2. 2 Buyer: View the OTP on your Dashboard. Relay it to the Agent.
  3. 3 Agent: Enter the correct OTP.
  4. 4 Logic Change: The status moves to DELIVERED. The system records the deliveredAt timestamp precisely.

6.2 Location Fingerprinting

During verification, the Agent's browser captures their GPS Coordinates. These are stored in agentLat and agentLng. An Admin can later compare these against the buyerLat/Lng to verify if the delivery actually happened at the correct house.

Enhanced Escrow — Chapter 7: Disputes

7. The Advanced Dispute Matrix

Conflict is inevitable in commerce. This software classifies disputes into three logical categories based on the **Transaction State** at the time of the claim.

Scenario Technical Status System Label
Doorstep Rejection AWAITING_OTP BOUNCED
Post-Delivery Flaw DELIVERED RECEIVED
No-Show Agent ESCROW_HELD NOT_DELIVERED

7.1 Scenario A: BOUNCED Logic

If a Buyer rejects an item at the door, the item is "Bounced". The Admin doesn't need to judge this. It follows an **Automated Return Flow**:

  • The Seller must confirm they have received the item back.
  • Once confirmed, the system triggers an automatic **Refund** to the Buyer.

7.2 Scenario B: RECEIVED Logic (24h Window)

This tests the protection window. Even after giving the OTP, the Buyer can raise a dispute if they find a defect. However, the system enforces a Strict 24h Timeout from the deliveredAt timestamp.

🚨 NEGATIVE TEST CASE

Try raising a dispute 25 hours after delivery. The backend will return an error, as the funds are already being processed for release to the Seller.

Enhanced Escrow — Chapter 8: Arbitration

8. Arbitration & Resolution Logic

When a dispute is not a "Bounce", the Admin must step in as the final arbiter.

8.1 Seller's Response Constraint

One of the most specific logic rules in the code is the **Post-Delivery Response Lock**.

  • Scenario: Dispute raised AFTER delivery (RECEIVED).
  • Rule: The Seller cannot add a comment to the dispute.
  • Logic: Since the handover was confirmed by OTP, the Seller's "word" is no longer relevant; the Admin must judge based on the Buyer's evidence and the Agent's photo/location data.

Test: Admin Settlement

  1. 1 Log in as Admin. Open the Dispute Queue.
  2. 2 Enter a decision reason (logged for auditing).
  3. 3 Refund Buyer: Moves status to REFUNDED.
  4. 4 Release Seller: Moves status to COMPLETED.

8.2 The 7-Day "Missing Agent" Lock

The system prevents Buyers from complaining too early. If a Seller hasn't shipped yet, the Buyer must wait **7 Days** before they can raise a NOT_DELIVERED dispute. This protects the logistics pipeline from premature cancellations.

Enhanced Escrow — Chapter 9: Security

9. Architectural Security Guardrails

This chapter covers the "Invisible" logic that ensures the system cannot be compromised by malicious actors or technical glitches.

9.1 JWT Bearer Token Security

Every single API request (except Login/Register) is intercepted by an **Authorization Middleware**.

  • Test: Remove the token from LocalStorage in the browser console.
  • Result: Every UI interaction must instantly fail or redirect to the Login screen.

9.2 ID Mutation & Ownership Checks

The system doesn't just trust the `userId` sent in the request body. It verifies it against the **Decoded JWT Payload**.

  • Test Case: Log in as Buyer A. Attempt to `GET /api/transactions/buyer/B`.
  • Result: The Backend will reject the request as the JWT ID does not match the request URL parameter ID.

9.3 Input Sanitization & SQLi

All user inputs (Product names, Dispute reasons, Full names) are sanitized through the **Prisma SQL Engine**. This prevents traditional SQL injection attacks by treating all input as parameters rather than executable code.
